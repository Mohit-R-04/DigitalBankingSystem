\section{System Architecture Overview}
%========================================================================

The Digital Banking System consists of 6 independent Spring Boot microservices
communicating through an API Gateway (synchronous REST via Feign) and Apache
Kafka (asynchronous events). All services are stateless and share no databases;
each service owns its own MySQL schema.

\begin{description}
  \item[API Gateway (8080)] Entry point for all client requests. Handles rate
  limiting (Redis-backed) and routes to the correct service.
  \item[Account Service (8081)] Owns account data in \texttt{account\_db}.
  Handles account creation, balance queries, debit/credit, blocking.
  \item[Transaction Service (8082)] Owns transfers in \texttt{transaction\_db}.
  Orchestrates the SAGA flow for money transfers and OTP verification.
  \item[Payment Service (8083)] Owns payments in \texttt{payment\_db}.
  Integrates with Razorpay for deposits/withdrawals.
  \item[Fraud Detection Service (8084)] Stateless. Consumes Kafka transactions,
  runs fraud checks using Redis, publishes results back.
  \item[Notification Service (8085)] Stateless. Consumes Kafka events and sends
  alerts (simulated via console logs).
\end{description}

\subsection{Communication Model}
\begin{itemize}
  \item \textbf{Synchronous (REST via Feign):} deduct balance, credit balance,
  refund, get balance, account queries.
  \item \textbf{Asynchronous (Kafka):} fraud checks, transaction completion,
  account blocking, OTP generation, all notifications.
  \item \textbf{Storage:} MySQL (persistent data), Redis (OTP, fraud counters,
  rate limiting).
\end{itemize}

\begin{lstlisting}[language={}]
Request body:
{
  "accountHolderName": "Mohit Reddy",
  "email": "mohit@test.com",
  "phone": "9876543210",
  "accountType": "SAVINGS",        // SAVINGS | CURRENT | FIXED_DEPOSIT
  "initialDeposit": 50000
}

Response (201 Created):
{
  "id": "de6556e5-...",
  "accountNumber": "378669440034",
  "accountHolderName": "Mohit Reddy",
  "accountType": "SAVINGS",
  "status": "ACTIVE",
  "balance": 50000.00,
  "dailyTransactionLimit": 100000.00,   // SAVINGS=1L, CURRENT/FD=5L

}

\textbf{Flow:}
\begin{enumerate}
  \item Gateway validates path and rate limit
  \item Controller calls \texttt{accountService.createAccount()}
  \item Service checks \texttt{existsByEmail()} --- if exists, throws Runtime\-Exception (handled by \texttt{GlobalExceptionHandler} $\rightarrow$ 400)
  \item Generates unique 12-digit account number via \texttt{SecureRandom}
  \item Sets daily limit based on account type (SAVINGS=1L, else 5L)
  \item Saves to MySQL (\texttt{account\_db.accounts})
\end{enumerate}

\subsubsection{GET /api/v1/accounts/\{accountNumber\}}
\textbf{Flow:} Gateway $\rightarrow$ AccountController $\rightarrow$ \texttt{findByAccountNumber()} $\rightarrow$ MySQL. If not found $\rightarrow$ Runtime\-Exception $\rightarrow$ GlobalExceptionHandler $\rightarrow$ 404.

\subsubsection{PUT /api/v1/accounts/\{accountNumber\}/deduct}
Called by Transaction Service (Feign client). Checks status is ACTIVE and balance sufficient, then subtracts amount. If insufficient $\rightarrow$ Runtime\-Exception $\rightarrow$ 500 (Feign error propagated to caller).

\subsubsection{PUT /api/v1/accounts/\{accountNumber\}/credit}
Called by Transaction Service (refund) and Payment Service (webhook credit). Adds amount to balance.

\subsection{Complete Transfer Flow (Happy Path)}

\begin{lstlisting}[language={},basicstyle=\ttfamily\footnotesize]
  Step  : Action                     Type        Actor
  ----- : -------------------------- ----------- --------------------------
  1     : POST /transfer             Sync (HTTP) Client -> Transaction Svc
  2     : deductBalance(sender,amt)  Sync (REST) Transaction -> Account Svc
  3     : Save transaction           Sync (JPA)  Transaction Svc -> MySQL
           status = PROCESSING
  4     : publish transaction.       Async       Transaction Svc -> Kafka
           initiated
  5     : consume & fraud check      Async       Fraud Detection Svc
  6a    : publish fraud.check.clean  Async       Fraud Svc -> Kafka
  6b    : publish verification.      Async       Fraud Svc -> Kafka
           required (if suspicious)
  7     : processCleanResult()       Async       Transaction Svc (consumer)
  8     : completeTransaction()      Sync (JPA)  Transaction Svc -> MySQL
           status = COMPLETED
  9     : publish transaction.       Async       Transaction Svc -> Kafka
           completed
  10    : creditBalance(receiver)    Async       Account Svc (consumer)

\subsection{Flow Diagram (Text Description)}
The complete SAGA transfer flow is described below as sequential steps.

\textbf{Normal (clean) transfer flow:}
\begin{enumerate}
  \item Client calls \texttt{POST /api/v1/transactions/transfer} with sender, receiver, amount.
  \item Transaction Service synchronously calls Account Service to deduct the sender's balance (Feign).
  \item Transaction Service saves the transaction with status \texttt{PROCESSING}.
  \item Transaction Service publishes \texttt{transaction.initiated} to Kafka.
  \item Fraud Detection Service consumes the event and runs three checks
  (velocity via Redis INCR, amount via Redis average, balance via Feign).
  \item If clean, Fraud Detection publishes \texttt{fraud.check.clean} to Kafka.
  \item Transaction Service consumes it and calls \texttt{processCleanResult()}, marking status \texttt{COMPLETED}.
  \item Transaction Service publishes \texttt{transaction.completed}.
  \item Account Service consumes it and asynchronously credits the receiver's balance.
  \item Notification Service consumes it and sends debit/credit alerts.
\end{enumerate}

\textbf{Suspicious (OTP verification) flow:}
\begin{enumerate}
  \item Steps 1--5 same as above, but Fraud Detection detects suspicious activity.
  \item Fraud Detection publishes \texttt{verification.required} to Kafka.
  \item Transaction Service consumes it, generates a 6-digit OTP, stores it in Redis
  (\texttt{verification:otp<txnId>}, 5-min TTL), sets status \texttt{PENDING\_VERIFICATION}.
  \item Transaction Service publishes \texttt{transaction.otp.generated} (Notification alerts user with OTP).
  \item Client calls \texttt{POST /{transactionId}/verify?otp=...}.
  \item If OTP correct, transaction completes and receiver is credited (same as steps 8--10 above).
  \item If OTP wrong or expired, the SAGA compensates: sender is refunded synchronously
  and the account may be blocked (see compensation section).
\end{enumerate}

\subsection{SAGA Compensation (Failure Path)}
When a transaction fails (wrong OTP or expired OTP), the SAGA compensates:
\begin{enumerate}
  \item Money already deducted from the sender in step 2 is refunded synchronously via
  Feign \texttt{creditBalance(sender, amount)}.
  \item Transaction status is set to \texttt{FLAGGED} with a failure reason.
  \item If OTP was wrong (possible fraud), \texttt{fraud.detected} is published so the
  Account Service blocks the account and Notification alerts the user.
  \item \texttt{transaction.refunded} is published so Notification informs the user
  the refund was processed.
\end{enumerate}

\subsection{OTP Verification Endpoint}
\textbf{POST /api/v1/transactions/\{transactionId\}/verify?otp=123456}

\begin{enumerate}
  \item Transaction Service finds transaction
  \item Reads OTP from Redis: \texttt{redis.get("verification:otp<txnId>")}
  \item \textbf{OTP null (expired):} compensateTransaction --- refund via Feign (SYNC), status=FLAGGED, publish \texttt{transaction.refunded}
  \item \textbf{OTP wrong:} blockAccountAndCompensate --- publish \texttt{fraud.detected} (async, blocks account), then refund via Feign (SYNC), status=FLAGGED
  \item \textbf{OTP correct:} delete Redis key, \texttt{completeTransaction()} --- status=COMPLETED, publish \texttt{transaction.completed}
\end{enumerate}

\subsection{Fraud Detection Service --- Three Patterns}

\subsubsection{Pattern 1: Velocity Check}
\begin{lstlisting}[language={}]
Key:    "fraud:velocity<accountNumber>"
Value:  transaction count (integer)

INCR key                     // atomic increment
if count == 1: EXPIRE 60s    // reset window after 60 sec
if count > maxTransactionsPerMinute (5): FRAUD

\subsubsection{Pattern 2: Amount Check (3x average)}
\begin{lstlisting}[language={}]
Key:    "fraud:avg_amount<accountNumber>"
Value:  running average amount

if avgKey null: SET to current amount, return NOT suspicious
else:
  threshold = avg * 3.0
  if amount > threshold: FRAUD
  newAvg = (avg + amount) / 2   // update running average

\subsubsection{Pattern 3: Balance Check (90\%)}
\begin{lstlisting}[language={}]
No Redis - uses account balance fetched via Feign:
  maxAllowed = balance * 0.90
  if amount > maxAllowed: FRAUD

\section{Transaction Status State Machine}
%========================================================================

\begin{lstlisting}[language={}]
              +--------------+
              |    PENDING   |
              +--------------+
                    |
                    | transfer() initiated
                    v
              +--------------+
              |  PROCESSING  |<---------------+
              +--------------+                 |
              |           |                    |
       clean  |           | suspicious         | OTP wrong/expired
              v           v                    |
   +----------------+  +--------------------+  |
   |   COMPLETED    |  | PENDING_VERIFICATION| |
   +----------------+  +--------------------+  |
                          |                    |
                     correct OTP               |
                          v                    |
   \subsection{Transaction State Machine}|   
   The transaction lifecycle follows a structured state progression:
   
   **PENDING** $
ightarrow$ **PROCESSING** $
ightarrow$ { COMPLETED, FLAGGED, FAILED }:
   
   - **PENDING**: Transfer initiated; transaction record created with
     INITIAL status; Razorpay deposit pending.
   
   - **PROCESSING**: Fraud velocity check runs; OTP verification begins.
   
   - **COMPLETED**: All checks passed; money credited to receiver;
     Kafka ``transaction.completed'' published; AccountService credits
     receiver's balance; transaction marked COMPLETED.
   
   - **FLAGGED**: Fraud detected (velocity > limit) OR OTP failed;
     sender's money refunded synchronously (SAGA compensation); account
     blocked; transaction marked FLAGGED with failure reason.
   
   - **FAILED**: Unexpected exception during processing; sender's money
     refunded automatically (SAGA compensation); transaction marked
     FLAGGED with failure reason.
   
   State transitions: PENDING $
ightarrow$ PROCESSING $
ightarrow$ {COMPLETED,
   |   FLAGGED, FAILED}. Order of checks matters: velocity INCR happens first,
   |   then OTP verification.
   +--------------+

\section{Key Design Decisions}
%========================================================================

\begin{enumerate}
  \item \textbf{Refund is synchronous (Feign)} --- Must confirm money returned before marking FLAGGED. Async would risk ``refunded'' status without actual refund.
  \item \textbf{Credit receiver is asynchronous (Kafka)} --- Transaction already marked COMPLETED; receiver gets money in background.
  \item \textbf{Block account is asynchronous (Kafka)} --- Fire-and-forget; no one waits.
  \item \textbf{OTP in Redis with 5-min TTL} --- Auto-expiry, no cleanup needed.
  \item \textbf{Velocity counter in Redis with 60s TTL} --- Atomic INCR, thread-safe, auto-reset.
  \item \textbf{Kafka key = transaction ID} --- Ensures ordering for same transaction.
  \item \textbf{Kafka 7.6 KRaft mode} --- No Zookeeper dependency.
  \item \textbf{Feign clients for sync calls} --- Deduct, credit, refund, get balance.
  \item \textbf{GlobalExceptionHandler} --- Converts RuntimeExceptions to proper HTTP codes (400/404/500).
  \item \textbf{GlobalExceptionHandler handles ``not found''} --- returns 404 instead of 500.
\end{enumerate}
